# Operations

## Environments and configuration

Production uses `docker compose` and `.env`. Development uses `docker compose --env-file .env.dev -f compose.dev.yaml` and a separate project, database, Redis and App registration. Never point both instances at the same database or GitHub webhook channel.

`CM_PUBLIC_URL` is the exact browser origin, including a development port. OAuth and installation callbacks use it. `CM_WEBHOOK_URL` overrides only the webhook destination. Use a dedicated Smee channel for local development and include `webhooks` in the persistent `COMPOSE_PROFILES` setting. Keep secure cookies enabled for HTTPS and disabled only for local HTTP. Setup reports inconsistent origins, cookies and webhook configuration before registering an App. Two login tabs have independent single-use attempts tied to a stable browser cookie; switching browsers still requires starting again there.

The production API binds loopback port 8080. Terminate TLS with a reverse proxy supporting WebSockets and long-lived connections. For Caddy, a minimal site is:

```caddyfile
reviews.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

Mortis is the only executable analysis engine. All inference uses an explicitly selected shared API connection; provider/auth/quota failures never switch it automatically. Keep one scheduler and the separate review, assessment/verification, summary, security, sync and graph queues. The OCR binary and official subscription clients/runner are absent from current images. Historical profiles are retained as private archives, not mounted into application services.

## Optional code graph parser

The isolated parser, authorized indexing, internal retrieval and browser repository activation remain available. Mortis PR analysis consumes exact-revision related source through the existing bounded retrieval; assessment and verification retain related-file discovery. Security scanning does not use graph enrichment. Independent read-only Code MCP remains available. Starting the optional parser does not opt repositories into graphs.

Indexing completion and coverage are separate. **Indexed** means the eligible files finished processing; files outside supported structural formats are counted separately. **Indexed with warnings** means parser warnings, invalid encoding or size limits left eligible content incomplete; available results remain usable. Repository configuration and PR Impact show counts and reasons. The API keeps `ready` / `partial` states, and `coverage.complete` stays false when visible files remain unsupported. Configured exclusions do not count as warnings or appear in visible coverage. A new extractor version creates new snapshot identities: the default branch refreshes normally, and administrators can index other exact revisions explicitly. Never relabel or rewrite immutable old snapshots to hide their warnings.

PR details expose **Code**. Diffs compare the saved PR merge base to head and work without enabling or building a graph, including text formats with no structural parser. Reading, searching and changing groups use GitHub read requests and existing saved summaries; they do not start indexing, reviews or model calls. Missing summaries leave All changes usable. Saved groups are withheld when revision or generation-input policy cannot be established. Inline findings require immutable source/path/range evidence; earlier or unknown locations remain separate.

The browser-only POST `/pulls/{id}/code/workspace` returns the current file inventory and one selected view in one response. Legacy `/code` overview and `/code/file` reads remain. All enforce current permissions and exclusions before and after reading content. They add no PAT/MCP access. A changed PR pair returns 409; use **Refresh Code**. Diff acquisition is bounded to 8 MiB decoded comparison JSON, four in-process immutable cache entries, 300 files, ten files per page, 256 KiB patches and 2,000 rendered rows. Full patches are checked for credential material before display limits. Missing patches are unavailable, not assumed binary or unchanged; Open on GitHub provides recovery. Permission revalidation still requires network requests even for cached comparisons. Responses are no-store. Only the mounted Code workspace retains reusable content, for an absolute 30 seconds per validated response, bounded to 5 MiB / 10 entries. An oversized active result is displayable but not retained on navigation. The visible view refreshes before expiry; hidden entries do not poll. Leaving Code, account/session changes, offline state and access/revision errors purge results. Search/group/page operations use the bounded inventory locally. Idle terminal-PR metadata polls every 30 seconds, open/active PRs every five seconds, and the sidebar every 60 seconds while idle or five seconds during known active work. Code/history do not poll detailed findings; tab totals come from PR metadata. The comparison stream has a 20-second elapsed budget checked between chunks and five-second I/O timeouts, with the existing maximum two attempts and one-second retry delay; permission calls retain their existing limits.

For a read-only latency probe, run `docker compose --env-file .env.dev -f compose.dev.yaml exec -T api python - --login LOGIN --pr-id ID --path PATH --samples 20 < scripts/check_pr_code_performance.py`. It prints timings/counts/bytes, not response content or credentials. It makes real GitHub permission/compare reads but starts no review, index or generation. The first Diff is a cold comparison acquisition; later warm samples retain two fresh permission gates. See [performance evidence](plans/pr-code/performance.md#delivered-results) before changing server capacity or authorization TTLs. Restart affected workers after shared GitHub adapter changes, draining active jobs first.

Dependencies, Definitions and Source retain their separate graph opt-in and exact head/merge-base snapshots. An administrator with GitHub write access can explicitly choose **Index selected revision** there; the existing `code-graph-worker` handles it. Disabled/missing/expired indexes only affect these secondary views. The latest default branch and up to ten recent usable revisions are retained for seven days. Source never substitutes another commit. Busy/missing retained objects can make source temporarily unavailable; use Refresh file. Graph cancellation/resumption and exclusions remain in Project context. See [PR Code validation](pr-code.md) and the historical [Phase 4 report](plans/code-graph/phase-4.md).

The parser and dedicated `code-graph-worker` services live directly in `compose.yaml` and `compose.dev.yaml`, behind the `code-graph` profile. Fresh `init-env` configurations include a separate `CM_CODE_GRAPH_TOKEN`; existing installations run `python3 backend/code_mortis/manage.py upgrade-env --file .env` (or `--file .env.dev`). This adds missing service tokens without rotating existing credentials or changing active profiles.

Set `COMPOSE_PROFILES=code-graph` in the instance environment file once. Preserve other enabled profiles; for development with the webhook relay use `COMPOSE_PROFILES=webhooks,code-graph`. Then use the normal commands: `docker compose up -d --build` in production, or `docker compose --env-file .env.dev -f compose.dev.yaml up -d --build` in development. No graph-specific Compose file or repeated `--profile` flag is required. Omit explicit `--profile` flags when using the persistent list, because those flags override `COMPOSE_PROFILES`. Coolify keeps its normal overlay; configure the profile and token in that deployment's environment. Starting the parser with an empty token fails immediately. Leaving the profile disabled requires no graph token and starts neither graph service.

Only the trusted graph worker and parser join the dedicated internal network. Index, refresh and cleanup jobs use the `code-graph` queue, with one active job per worker. Reviews keep their own worker and queue. The graph worker uses the existing application image and has a one-CPU, 768 MiB memory/no-swap ceiling, 128 MiB temporary storage and 64 process IDs; the parser limits below are separate. These limits bound graph services, but both still share host CPU, disk and database capacity with reviews. That network is declared even while the optional parser is disabled. The parser gets only its service token, with no app env file, GitHub/database/Redis/model credentials, source volume or Docker socket. Keep one parser replica and one ASGI worker. Limits are one CPU, 256 MiB total memory with no swap, 128 MiB temporary storage, 32 process IDs and a 120-second request deadline. A busy parser rejects additional extraction; an oversized, malformed, timed-out or killed extraction fails explicitly and cannot publish a usable snapshot. A worker disconnect kills the active parser child. No embedding/model API is involved.

In a repository, open **Configure → Project context → Code graph**, switch it on and Save. This is independent of Enable reviews and requires a browser administrator with current GitHub write access. Existing repositories remain off. The enabling user is recorded; queued work rechecks that user’s membership and repository access. The existing reconciliation schedule checks enabled repositories for default-branch changes. A failed refresh keeps its diagnostic visible and waits one hour before automatic reconciliation tries again, instead of creating a new failed job every five minutes. Explicit Retry bypasses this cooldown; successful refreshes return to the normal schedule. Cooling-down repositories do not occupy the reconciliation batch. Status shows queued/running/ready/partial/stale/failed/cancelled, the observed revision and previous usable revision. Retry explicitly resumes failed/cancelled attempts and records the requesting administrator. Cancel pauses automatic updates until Retry or disabling/re-enabling. Saving off cancels active work and stops code access; retained data follows the existing cleanup policy. Existing PAT and MCP grants cannot read or manage code graphs.

For new eligible Mortis PR runs on an opted-in repository, the review worker can include up to three complete related files and 12 KiB of related source per assigned-file request, with 48 KiB reserved across the run. These are optional source limits, not model-token budgets. Shared-connection prompt ceilings, stage budgets and reported-usage accounting still apply. Matching requires the exact PR head, extractor and exclusion policy; deleted assigned files omit graph context. Missing indexes are requested on `code-graph-worker` without delaying the current review, so an initial review can run normally and a subsequent new review may use the completed index. A retry preserves its attempted selection, even if an index becomes available later. Paused indexing does not prevent reading a usable existing index; disabling the repository graph stops future enrichment.

Assessment and fix verification through shared connections can use up to three related-file suggestions at the exact current SHA. Suggestions are not citations: needed source is requested and validated through the existing evidence loop. The graph actor and policy are rechecked before each round. Mortis initial analysis receives selected graph sources; historical OCR omission records remain unchanged. Existing PAT/MCP-origin runs remain excluded. See [phase 2 details and evaluation protocol](plans/code-graph/phase-2.md).

The run's `code_graph` configuration records eligibility; checkpoint/report `code_graph` entries record selected paths, immutable blob/revision identity, limits and omission reasons. They do not store additional raw source. Readiness describes the default branch, so it does not promise that a particular PR head is indexed. The initial Mortis request includes selected graph source without displacing mandatory assigned code; existing PAT/MCP-origin reviews remain excluded from graph context at every stage. Added context may increase tokens; the completed scoped real-model evaluation did not establish benefit. Keep enrichment experimental and opt-in; see the Phase 2 report for the full comparison and citation limitations. The recorded local overlap workload peaked at 2.49 GiB of container memory under a 4.87 GiB Docker ceiling; model replies were stubbed and Trivy vulnerability data was stale, so this is not a general 8 GB production guarantee. After updating review-context code, drain and reload review/verification/summary/security/sync/graph workers and scheduler; no database migration or new mount is required.

To disable the service, first turn off the repository settings, let active graph work finish, then stop `code-graph-worker code-graph-parser` with the normal Compose command, then remove `code-graph` from `COMPOSE_PROFILES` while preserving other profiles. Removing a profile alone does not stop an already running container. The parser has no persistent data volume to delete.

Indexing uses the named `code-graph-data` volume on the trusted graph worker, owned by UID/GID 10001. The trusted API mounts this same volume read-only for Code MCP source reads. Rebuild the application image before starting services so a new volume gets the correct ownership. Keep one graph writer and a POSIX-lock-capable shared volume: source readers take shared locks and acquisition/retention take an exclusive lock. The isolated parser never mounts it. The volume contains private repository Git objects, including excluded files retained as part of a commit, even though excluded bytes never go to the parser. Protect its backups like the source repositories.

Back up `code-graph-data` together with PostgreSQL while graph work is stopped. Restoring graph rows without this volume leaves source unavailable; lookup must never substitute another revision. Retention keeps the latest successful default-branch snapshot plus up to ten other usable snapshots for seven days, removes terminal attempt records after seven days, and prunes orphan graph refs/objects under the shared lock. A periodic cleanup job runs only after graph configuration/work exists. Failed/cancelled attempts require explicit retry; successful identities remain immutable. Do not delete Git refs manually while workers run. Graph cleanup never deletes saved review evidence. Missing objects require restoring the matching volume or a deliberate graph-cache rebuild through an operator-controlled cache rebuild while graph work is stopped; Retry does not rewrite immutable ready snapshots.

Initial indexing admits at most two pending snapshots per repository and sixteen per instance, with one extraction at a time. Git acquisition monitors 256 MiB per repository and 1 GiB total on disk, alongside the parser's source limits. These polling limits can overshoot during a fetch and are not hard disk quotas. Disabling the parser profile does not erase retained graph data or change repository opt-ins; disable repository opt-ins separately if code access must stop. A missing parser produces a failed indexing attempt with an explicit Retry action after infrastructure is restored.

The current tree admission limit counts all Git tree entries, including excluded and unsupported files: 1,000 total, alongside 1 MiB per admitted file and 8 MiB total source. Oversized trees fail explicitly. See [measured storage and corpus limits](plans/code-graph/phase-1d-1e.md); these measurements do not establish full-stack 8 GB capacity.

When upgrading an installation that ran graph jobs on `review-worker`, build the new application image first, pause the scheduler and cancel the affected review/sync queue consumers, then wait for their active and reserved tasks to finish. Recreate `review-worker`, `sync-worker` and `scheduler` and start `code-graph-worker` using the normal Compose file and enabled profile. Keep the existing `code-graph-data` named volume. No schema migration, re-index, broker purge or manual job reset is needed for this change. New workers acknowledge old graph deliveries on `reviews` without claiming an attempt; the dispatcher resends their durable queued jobs to `code-graph`. Verify one graph queue consumer, review queue isolation, retained refs and `/health/ready`. See the [migration checklist and rollback](plans/code-graph/plan.md#dedicated-graph-worker-migration-completed-locally).

To verify locally, run `python3 scripts/check_code_graph.py` from the repository root. It builds disposable images, verifies the real private-network transport, and tests cancellation, the full deadline, tmpfs exhaustion and memory enforcement. It uses a separate Compose project and removes that project's containers/network afterward. Run ordinary backend graph tests against `compose.test.yaml`. The optional test stack is `compose.code-graph.test.yaml`; the existing database/test services remain separate.

The protocol, publication and retention requirements are documented in [checkpoint 1B and the handoff](plans/code-graph/plan.md#phase-1-execution-checklist). These parser limits alone do not establish full-stack operation on an 8 GB server; the Phase 2 report records a bounded overlap workload and its limits.

Code file rows automatically show a check when saved validated coverage confirms that file's selected review items completed or were reused at the current base/head. No checkbox, extra table, migration or environment flag is required. Missing/earlier/malformed coverage cannot establish a check. Current open-finding indicators show `3+` or `?` when bounded evidence cannot establish an exact count. Neither a reviewed check nor an absent finding indicator establishes a clean review. See [workflow acceptance](plans/pr-code/review-workflow.md).

## Upgrade an existing installation

1. Back up PostgreSQL and `.env`, retain any historical native profiles, and drain/cancel active work. Stop API/webhook admission, scheduler, every application worker and the old runner before cutover; keep PostgreSQL/Redis available. Stop graph writing before backing up `code-graph-data`.
2. Build the intended image. `python -m code_mortis.manage upgrade-env --file .env` adds a missing parser token without replacing existing keys. Never regenerate the encryption key of an existing database.
3. Run `docker compose run --rm migrate`. The Mortis-only migration changes only future repository engine settings; saved runs, plans, findings and engine identities stay unchanged. Historical subscription credentials are never converted into API credentials.
4. With all old processes/requests stopped, run `docker compose run --rm api python -m code_mortis.manage retire-subscriptions`, then `docker compose run --rm api python -m code_mortis.manage retire-ocr`. These settle unfinished retired work explicitly and preserve completed results and known/unknown accounting. The OCR cutover releases its stranded connection slots only after process termination. Select a shared connection for future work. Explicitly start a new Mortis run instead of resuming a saved OCR plan.
5. Remove only the stopped retired runner container; preserve its profile volume. Start current services with `docker compose up -d`, then verify readiness and worker queues. Existing App IDs, registration URLs, credentials and webhooks are unchanged. Keep automatic reviews off while doing provider-free checks; enabling them or pressing Review/Scan/Test connection performs real external work. Do not claim provider/GitHub integration from readiness alone.

See [GitHub registration settings](https://docs.github.com/en/apps/maintaining-github-apps/modifying-a-github-app-registration). Never start two active copies of a restored instance against GitHub.

## GitHub review checks

After deploying the check migration, open the existing GitHub App's **Permissions & events** settings. Add **Repository permissions → Checks → Read and write** and save. Confirm the **Check run** webhook subscription, then approve the new permission in each account's installed-App settings. Do this separately for development and server Apps; retain their existing credentials, callbacks and webhook URLs. New registrations request the permission automatically.

Reviews and comments keep working while approval is pending. The run page shows the permission error under **GitHub check**. Permission acceptance triggers recovery, with periodic reconciliation every five minutes as a fallback. No model rerun is needed to repair a check update. If an installation is removed, remote checks cannot be updated until access is restored; the app retains the synchronization error.

The check is queued while waiting, in progress during analysis and publication, and successful only after full coverage and comment publication. Findings do not fail a completed check or approve the PR. Partial coverage, execution errors and publication failures fail it; timeouts, cancellation, skipped work and blocked authentication/quota have distinct conclusions. Repository branch-protection settings are unchanged.

GitHub's per-check **Re-run** requires an enabled Code Mortis member with current repository write access. It rejects closed PRs and obsolete commits. For complete analysis with failed publication it retries saved comments; for blocked work it resumes the existing run. Other retries create a new manual run with current repository settings and the original connection. Retired engine plans cannot resume; new work requires a shared connection and never changes provider implicitly. Use Code Mortis to cancel a running review; its check follows the cancellation. Check-suite-wide reruns are not handled.

Checks are added to new runs and unfinished work during migration, not completed historical runs. Details links use `CM_PUBLIC_URL`; development localhost links are reachable only on the development machine. Check metadata and errors are included in normal database backups. Logs identify `sync_check` jobs and their run IDs; repeated GitHub failures recover independently of paid review execution. Never mark a check successful manually to hide missing coverage or failed publication.

## Backup and restoration

PostgreSQL owns durable jobs and history. Redis can be rebuilt. Back up `.env` separately in encrypted storage; database ciphertext requires the original `CM_ENCRYPTION_KEY`. Retain pre-retirement profile archives privately if present, but current Mortis services do not read them. Never upload credentials or profile archives as diagnostic attachments.

With work quiesced, make private backups. When graph indexing is enabled, also drain and stop `code-graph-worker` and back up `code-graph-data` with the matching database as described above:

```sh
umask 077
docker compose exec -T postgres pg_dump -U mortis -d mortis -Fc > mortis.dump
```

Copy `.env` into your encrypted backup store. Keep existing historical profile volumes intact when removing retired containers. Restart services only when the backup is complete.

Restore into a **new isolated installation**, retaining the original encryption key and matching App settings. Do not start workers while restoring:

```sh
docker compose up -d postgres redis
docker compose exec -T postgres pg_restore -U mortis -d mortis --no-owner --exit-on-error < mortis.dump
docker compose run --rm migrate
docker compose up -d
```

Inspect pending work before enabling dispatch or accepting webhooks. When restoring a pre-retirement backup, apply the migration and both retirement commands with consumers stopped before starting services. Keep saved engine identities and historical results intact. Test restoration privately before returning service to users.

The repository includes `backend/tests/restore_smoke.py` for a disposable database restored from an offline copy of the original volume. It fingerprints original columns and verifies that additive migrations preserve every old record. Its source/target names are deliberately restricted; see [acceptance evidence](acceptance.md) for the completed test.

## MCP access

Authenticated MCP is implemented in this codebase and off by default. Upgrade adds tables through additive migration `20261024_mcp` and the pinned `mcp==2.3.0` dependency, so rebuild the dependency image (`docker compose build`) and run `docker compose run --rm migrate` before starting workers. Restart `review-worker`, `security-worker`, `verification-worker`, `summary-worker`, `sync-worker` and `scheduler` after the code change so provenance validation and cleanup run everywhere. No GitHub App permission change is needed for MCP itself.

Settings → MCP access holds independent Reviews, Security, Code, and management switches. Each domain defaults off when first introduced; existing domain settings are preserved. Each switch takes effect without a restart. Disabling a domain immediately revokes its grants and refresh families; clients must consent again after re-enabling. Management tools remain available only on Reviews/Security. Administrators also manage the allowed client-metadata hostnames and pre-registered clients there. Members see only the instance status and their own connected grants with revoke controls.

The three resource endpoints live on the public origin: `CM_PUBLIC_URL/mcp/reviews`, `CM_PUBLIC_URL/mcp/security`, and `CM_PUBLIC_URL/mcp/code`. Discovery metadata is served at `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource/mcp/{reviews,security,code}`; the OAuth endpoints are `/oauth/authorize`, `/oauth/token`, `/oauth/revoke` and `/oauth/register`. Tokens never cross resource boundaries. The isolated graph parser receives no database or GitHub credentials and no repository MCP configuration.

Code MCP requires both the instance's Code switch and a per-repository code graph opt-in in Configure → Project context, followed by separate browser consent for `code:read` and selected repositories. Only currently visible opted-in repositories are offered. The seven tools list eligible repositories, inspect readiness, search definitions/literal text, read symbols/source, follow file imports and compare two indexed commits. They never index, run models or write to GitHub. `code_index_status` without a SHA reports the last observed default-branch commit; all navigation uses an explicit 40-character SHA. An unindexed requested commit stays unavailable even if an older snapshot exists. Uncommitted local edits are absent.

Code responses bound source to 64 KiB, search to 100 results and ten source files per page, traversal to two hops/500 visited files/100 returned edges, and impact to ten changed paths per page. Reuse `next_cursor` with the same search/revision; for a source excerpt continue from its `start_byte` at the same path/revision. Byte offsets refer to the original UTF-8 blob. Coverage counts include only visible files. Credential-bearing or otherwise unsafe source is withheld before slicing, so pagination cannot expose secret fragments. Files/symbols are untrusted data and never agent instructions. Missing or busy retained objects return unavailable and can be retried; callers/references remain explicitly unsupported. No embeddings, vector database or paid inference are involved; the consuming agent still spends tokens on returned context.

For the Code MCP upgrade, use the existing Compose file and recreate the API so its new read-only mount takes effect. Drain and reload workers that use the changed shared authorization/retrieval modules, then restart the scheduler. No new migration, service, graph rebuild or additional repository opt-in is required. Turning off Code MCP revokes external code grants without changing review history or repository indexing. Disabling a repository graph blocks its future code reads. See [Phase 3 evidence](plans/code-graph/phase-3.md) for the distinction between local transport tests and a real externally authorized client.

Each connection starts in the browser. The agent directs the user to `/mcp/authorize?request_id=...`, which requires the normal GitHub login and shows the client, exact callback, domain, repositories and permissions. Read permissions start selected; write, run and management permissions need explicit selection, and at least one repository is required. Deny returns an access-denied redirect to the client. Grants last 30 days, access tokens 15 minutes, authorization codes 60 seconds single-use; refresh tokens rotate atomically and reuse revokes the family. Each user holds at most 100 active grants; the instance holds at most 1000 registered clients. Revoking a grant in Settings → MCP access stops new MCP work at once and cancels that grant's queued, running or blocked reviews, scans and jobs while preserving saved results and unrelated work.

Client registration accepts pre-registered public clients with exact redirect URIs (PKCE S256 required, at most 10 URIs, no secret). Otherwise the server fetches Client ID Metadata Documents only from administrator-allowed hostnames over HTTPS with a 5 second timeout, 64 KB cap, no redirects, no private or metadata addresses and a pinned resolved IP. Dynamic registration at `/oauth/register` is a compatibility path only: it requires an enabled domain, allows loopback or allowed hostnames, and is limited to 20 requests per minute per address.

Public security-issue publication and destructive management actions pause for human approval. The agent receives an approval URL of the form `CM_PUBLIC_URL/mcp/approvals/<id>`; the owner opens it in the browser, checks the exact arguments and summary, then approves or denies. Approvals expire after 5 minutes, are single-use, and are bound to the granting user, tool and argument digest. Shared connection credentials remain encrypted server-side; retired subscription authentication tools are unavailable. Raw tokens, codes and refresh values are never logged; only their hashes are stored, and the audit keeps tool, outcome and duration without arguments.

Limits and retention are enforced per minute: OAuth and tool calls 120 per address or grant, registration 20 per address, with `Retry-After: 60` on 429. The periodic reconciliation task deletes expired authorizations, tokens, operations and approvals, and audit rows older than 30 days; review and security history is never touched by this cleanup.

Troubleshooting: 401 means the token expired, the grant was revoked, or the wrong resource was requested, so connect the client again. 403 means the domain is disabled, the scope or repository was not granted, or the role changed, so check Settings → MCP access and re-consent. 409 means a code, refresh token, request key or approval was replayed, the arguments changed, or the approval expired or was already decided, so ask the agent for a fresh preview instead of retrying blindly. 422 on consent means the submitted scopes or repositories fall outside what was offered. After any disable or role change, revoke and re-consent; reusing an old code or refresh token revokes the family by design.

## Personal API tokens

Members create named personal API tokens in Settings → API tokens and use them from Noodle or scripts. A token acts as its owner, further restricted by its selected permissions and repositories. It never gains authority its owner lacks.

Deploy every PAT-aware worker before opening token creation: API, review-worker, sync-worker, scheduler, and the security/verification/summary workers. Older workers do not enforce PAT origin gates, so rolling restarts must finish while admission stays closed. Run `docker compose run --rm migrate` for the additive token tables first, then restart all workers using the existing upgrade procedure. Creation stays closed until `GET /health/ready` passes and every worker runs the new code.

Token setup: issuing requires a GitHub callback completed within the previous 15 minutes; otherwise Settings reports `reauth_required` and the member signs in again. Expiration is required, default 30 days, maximum 365 days, measured in server UTC. At most 20 active tokens per user. The full value is shown once with `Cache-Control: no-store`; only its hash is stored. A lost value cannot be recovered: revoke the unused record and create another. Replacement is create, update clients, verify, then revoke the old token. Signing out of the browser does not revoke tokens; removing membership or disabling the account revokes them permanently, and re-adding the account never resurrects old credentials.

Expiry and revocation are enforced at admission, each paid stage, each GitHub publication batch, and recovery/retry. Revocation commits first, then an internal cleanup job cancels only that token's unfinished work through the existing review/scan lifecycle; completed results and remote publication IDs stay. An external request already sent cannot be unsent. To revoke in an incident, delete the token in Settings or remove the member, then confirm its queued work drained before considering the incident closed.

Limits are abuse protection, not spending limits: 20 failed authentications per minute per client IP, 120 accepted requests per minute per token, 10 creations per minute per user, with 429 and `Retry-After`. If the limiter is unavailable, PAT admission and creation fail with a recoverable 503 rather than falling back to a browser session or issuing a secret. Browser-session revocation still commits through PostgreSQL while Redis is down; durable cleanup retries later.

PATs authenticate only through the Authorization header over HTTPS (local HTTP development origins excepted). Missing, malformed, expired, or revoked credentials return 401 with a Bearer challenge; insufficient scope or current permission returns 403, with resource-hiding 404 retained where the route already hides. A request carrying both an Authorization header and `cm_session` is rejected. Token values never appear in logs, errors, job payloads, URLs, or telemetry; the `cm_pat_` format is redacted by the shared scrubber.

When a reverse proxy terminates HTTPS, configure Uvicorn's `FORWARDED_ALLOW_IPS` in the deployment environment with the proxy's exact source IPs or networks, and have the proxy set `X-Forwarded-Proto`. The API uses the ASGI scheme and client address; it never trusts forwarding headers itself. Keep the API port private and avoid trusting arbitrary peers with `*`. Without trusted proxy configuration, a forwarded HTTP connection is refused even when the public URL uses HTTPS. Cleartext development requires `CM_COOKIE_SECURE=false`, a configured local HTTP public URL, and a local request hostname.

A code-only rollback is unsafe while PAT-origin work is queued. Before downgrading: stop admission, revoke tokens, cancel and drain their unfinished jobs and pending publication/sync intents, then verify no executable PAT-origin work remains in `Job.payload["pat"]`, `ReviewRun.progress["pat"]`, `SecurityScan.progress["pat"]`, `Finding.sync_intent["pat"]`, or `SecurityFinding.issue["pat"]`. Only then restore old code while retaining the additive tables and history. Never delete the token tables as a rollback shortcut.

Troubleshooting: 401 means the value is missing, malformed, expired, or revoked, so create a replacement. 403 means the token lacks the permission or the owner lost the repository access, so check the token selection in Settings and current GitHub permissions. 429 means the per-token or creation limit was hit, so wait for `Retry-After`. 503 on PAT admission means the limiter is down, so retry without changing credentials.

## Diagnosis

For OpenCode Go, select the OpenCode API provider and set the base URL to `https://opencode.ai/zen/go/v1`. Muse Spark 1.3 Contributor uses model ID `muse-spark-1.3-contributor` and the `openai-responses` protocol. Code Mortis supplies its own User-Agent and a fresh `x-opencode-session` for each durable Mortis inference session, preserving it across its calls. These headers are generated for the Go endpoint, not stored as static connection headers. The connection test reports bounded provider errors with stored credentials redacted. See [OpenCode Go client requirements and endpoints](https://opencode.ai/docs/go/). Contributor prompts and completions may be used for Meta model training; consider this before sending repository content.

Every HTTP response has an `X-Request-ID`; callback errors display that diagnostic ID. Job logs contain job ID, kind and error class. Runs retain their IDs, pinned commits, connection, owner, initiator, engine, verified progress and publication state. Webhook delivery IDs are persisted for deduplication. OAuth codes and raw provider requests are not logged. Do not put secrets into model IDs, rules, background text, options or URLs.

| Startup | `docker compose ps` and `GET /health/ready` verify API, PostgreSQL and Redis. Inspect migration logs before retrying a failed startup. |
| GitHub login | Check browser origin, callback URL and cookie scheme. An expired, cancelled, replayed or different-browser attempt shows a recovery action. Start a fresh login; do not disable state checks. |
| Installation | Match the dedicated setup URL. Sign in if installation began at GitHub, then validate available installations with the user API. An installation ID is not authorization. |
| Webhook | Check GitHub deliveries and relay connectivity in development. Verify destination and signature secret. Duplicate delivery IDs are acknowledged without duplicate work. |
| Permissions | Check current repository access, installed repositories and instance membership. Reading requires access; manual reviews and finding mutations require write access. Removal/revocation prevents consumption. |
| API connection | Test connection performs a direct shared-provider tool call. Check protocol, tool support, model, endpoint and provider quota. No native subscription tokens belong here. |
| Quota or expired session | The run is blocked, with a reason. Restore usage or reconnect the same account, then **Resume review**. Saved completed file checkpoints are reused. No automatic fallback to another account, model or paid API. |
| Git fetch | Temporary worker filesystems are intentionally `noexec`. GitHub installation credentials are supplied through URL-scoped Git configuration in the fetch process environment. They are not written to a helper script or included in model context. Keep `noexec` enabled; a helper permission error indicates an older worker that needs the fetch correction and a restart. |
| Mortis token budget | Durable stage reservations include estimated input and allowed output before dispatch; actual reported consumption reconciles afterward. Unknown usage retains the reservation and blocks further paid work. Provider totals can exceed estimates; limits are not a dollar guarantee. Explicitly change repository budgets for future work; cancellation cannot recover consumed tokens. |
| Review | Queued work needs scheduler and review worker. Failed or partial coverage is not a clean review. Context, task, token and deadline limits remain enforced; cancellation preserves validated checkpoints and uncertain consumption. |
| Publication | Retry publication from the run. Saved findings are reconciled against GitHub markers first. New commits supersede old work; publication retry does not rerun analysis. |
| Resolution | Pending state remains visible until GitHub confirms. Retry a failed operation. Periodic reconciliation recovers missed events; absent later findings are not resolved automatically. |

`GET /health/live` proves only the API process is alive. Readiness does not prove workers, GitHub or a paid provider work. Inspect connection status, background errors and real runs separately. Useful logs:

```sh
docker compose logs --tail=100 migrate review-worker verification-worker summary-worker security-worker sync-worker scheduler
```

## Access and recovery boundaries

Only explicitly allowed members can use an instance. The initial owner binds to a numeric GitHub ID. Shared connection selection does not grant repository permission: current GitHub access and request provenance are revalidated before execution. Historical subscription records remain readable, while authentication and delegated execution are retired.

Reverse proxies must not record request bodies, authorization headers or sensitive callback query strings. Never expose provider credentials to browser clients or repository processes.

The database persists queued work before dispatch. Worker leases recover interrupted jobs; repeated process failures become visible after three attempts. Publication reconciles uncertain responses before a retry. History is retained indefinitely. Review content and model output remain untrusted and need human judgment; no scripts or generated changes are executed.
