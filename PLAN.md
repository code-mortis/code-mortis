# Code Mortis implementation plan

The [engine replacement roadmap](ENGINE_PLAN.md) defines the current implementation: Mortis Engine for PR reviews and security scans, shared API connections only, with existing exclusions, limits and code graph retained. The owner authorized personal early adoption on November 8, 2026. That decision does not turn pending or failed experimental checks into passes; M5 evidence and remaining uncertainty stay in [ENGINE_M5.md](ENGINE_M5.md).

OCR and official-client execution are retired. Existing engine identities, immutable plans, results, findings, coverage, resolution and consumption remain historical evidence. New repository settings select Mortis additively; saved OCR work is stopped explicitly, never converted into a Mortis plan. The complete self-hosted product remains the intended delivery, with production and real-account evidence tracked separately from local checks.

## Architecture

Keep FastAPI, Pydantic, SQLAlchemy, Alembic and PostgreSQL; Celery/Redis with separate review and synchronization queues; React, TypeScript, Vite, React Router, TanStack Query, Tailwind CSS and shadcn/ui. Use locked dependencies and the project-owned Mortis engine/prompts; deterministic security checks retain pinned Trivy.

Production serves the compiled frontend and API from one HTTPS origin. Development uses an independent Compose project with Vite HMR in Docker at localhost:5173, backend reload, separate secrets/volumes and a separate GitHub App. `CM_PUBLIC_URL` is the callback origin; `CM_WEBHOOK_URL` is the independently reachable webhook destination. Mortis runs in the trusted review/security workers through the shared inference gateway. Models receive only explicit, bounded context and restricted source reads; no native-client runner or OCR CLI is installed.

## Required behavior

- GitHub provides application identity and current repository permissions. Numeric membership identity survives username changes. An `installation_id` alone grants no access. App registration, login and installation are separate; request_oauth_on_install is disabled.
- Personal API tokens let members use Noodle and scripts with explicit permissions, selected repositories, required expiry, and revocation enforced through delayed work. Browser login and MCP OAuth remain independent; sensitive administration and public security-issue publication stay browser-only. See [token implementation and acceptance](docs/api-tokens-plan.md) and the [route policy](docs/api-token-route-policy.md).
- Shared API connections use the maintained provider catalog and OpenAI Chat Completions, Responses, Anthropic and Bedrock protocols, including OpenCode and compatible endpoints. Connection tests exercise tools. Reject incompatible settings before execution.
- Shared API connections are the sole execution mode. Retired subscription setup and execution return explicit errors; owner-only revocation and historical readers remain. Each run records initiator, trigger and immutable configuration. Revalidate repository and connection access before execution. Quota, authentication and availability failures never switch provider or connection silently. Revocation stops new consumption and cancels affected work.
- Mortis selects files using the shared file policy and trusted-base review rules. Application-assigned result groups determine verifiable coverage. Validate schema, paths and line ranges. Preserve complete, partial, failed, skipped, superseded and cancelled states independently from publication.
- Untrusted PR content cannot load scripts, hooks, agent configuration or MCP servers. Model source tools only read authorized exact-revision context and cannot write or execute commands.
- Persist webhook deliveries and jobs before acknowledging them. Persist results before publishing COMMENT reviews. Reconcile uncertain writes before retrying; publication retries do not repeat inference. Check head commits again before publication.
- Findings have current state and immutable historical occurrences. Missing later means not observed. Resolve/reopen in either system, dismiss with a reason, display pending GitHub changes and recover lost events periodically.
- Preserve existing users, repositories, API credentials and history through additive migration. Preserve retired engine snapshots and structured diagnosis without secrets.
- Keep English UI and configurable comment language. Public SaaS, billing, GitLab and automatic code changes are excluded.
- Authenticated MCP access is part of the product: independent reviews, security and code endpoints plus separately authorized management tools, all default off, with per-user browser consent, explicit repository selection, exact-argument approvals for public or destructive actions, grant provenance with revocation, and audit retention. Operator setup and troubleshooting are in docs/operations.md; evidence boundaries are in docs/acceptance.md.

## Future feature plans

- [PR Code browser](docs/pr-code-plan.md): local delivery of a PR diff workspace replacing Impact, reusing exact-revision summary groups and saved finding occurrences. Core diff navigation works independently of graph readiness; graph relations remain optional. Implementation and local verification are recorded in [PR Code delivery](docs/pr-code.md); generated tours with line anchors are deferred.
- [PR Code performance](docs/pr-code-performance-plan.md): implemented and verified locally. One authorized workspace response, pooled GitHub connections and bounded current-workspace reuse reduce measured Dependencies entry from 3.9s to a 0.97s median; valid cached switches take about 25–29ms and idle calls fall from 41 to 5/minute. Fresh access checks remain; production rollout is separate.
- [PR Code review workflow](docs/pr-code-review-workflow-plan.md): implemented locally. Automatic reviewed-file checks from validated coverage, previous/next navigation, current finding indicators and the existing bounded diff preserve the existing UI and performance limits. No manual checkbox or new persistence; folder trees, split diffs and generated tours remain separate.
- [Optional code graph](docs/code-graph-plan.md): Phase 0 and checkpoints 1A–1E are implemented locally: contracts, isolated parsing, authorized indexing/retention, bounded exact-revision retrieval and browser repository opt-in/readiness. Graph indexing, refresh and cleanup use a dedicated optional worker in the existing Compose stack. The historical Phase 2 native-client work added bounded exact-commit context and related-file discovery. Current eligible Mortis PR reviews consume the retained graph retrieval for initial analysis, assessment and verification; required source keeps priority and omissions remain explicit. Security scans do not have the same graph enrichment. The bounded local resource experiment is recorded; the historical native-client real-model evaluation is complete with 18/18 results and 306,289 reported tokens, but did not establish benefit and does not validate the current Mortis engine; enrichment remains experimental and opt-in; Phase 3 implements seven read-only tools on an independent, default-off `/mcp/code` resource with separate `code:read` consent and selected opted-in repositories. An authorized real MCP SDK client completed exact-revision navigation and temporary-grant revocation locally. Phase 2D prioritizes direct dependencies and preserves full assigned source, validated by three provider-free cases and 2,883 backend tests. No real repository is opted in automatically. No embeddings or pgvector are required; the recorded modest stack workload fits below 8 GB, while real-model overlap and general production capacity remain unverified. See the plan and [validation report](docs/code-graph-phase2.md) for the Phase 2 handoff, and the [Phase 3 report](docs/code-graph-phase3.md) for external navigation and its verification boundaries. Phase 4 adds an Impact tab with an immutable PR comparison, head/merge-base selection, supported file relationships, definitions, exact source and saved-finding links. Indexing a missing revision is explicit, browser-administrator-only work on the existing graph worker. See the [Phase 4 report](docs/code-graph-phase4.md) for completion evidence and verification boundaries.

## Definition of done

Done requires current Mortis PR review and security workflows, deterministic scanners, shared connections, history and code graph to meet their recorded contracts in development and on the server, with actual evidence for each acceptance claim. Retired subscriptions and OCR are historical compatibility requirements, not runnable acceptance targets. Local mocked checks, historical live evaluations and current real integrations are recorded separately. Missing external accounts, permissions or quota mean pending validation, not completion. See [acceptance record](docs/acceptance.md).
